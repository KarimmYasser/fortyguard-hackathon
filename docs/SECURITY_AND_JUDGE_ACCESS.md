# Security and Judge Access

## Required judging access

The official hackathon material requires:

- a working live demo that opens in an incognito browser without installation; and
- a public or judge-accessible repository. Private repositories must grant FortyGuard access through `Hackathon-FG` / `hackathon@fortyguard.com`.

Accordingly, the final judge-facing production domains must not require Vercel team authentication:

- <https://www.thermal-sentinel-grid.live>
- <https://thermal-sentinel-grid.vercel.app>

The GitHub repository may remain private as long as the official `Hackathon-FG` invitation has been accepted. A pending invitation is not completed access and must be checked before submission.

## Current controls

- Vercel's automatic platform DDoS mitigation remains the first network layer.
- Vercel Firewall denies irrelevant WordPress/Shopify probe paths before application execution.
- Paid live operations (`POST /api/v1/scan` and `POST /api/v1/dispatch/run-mitigation`) share an edge limit of eight requests per source IP per hour. This protects FortyGuard/LLM calls while allowing a judge to compare the four preset locations and execute the agent.
- Identical vendor requests use durable request-addressed cache entries.
- Identical simulation requests use permanent content-addressed solve results.
- CORS permits only the two production origins, the apex custom domain, and local Vite development origins.
- Browser responses include `nosniff`, clickjacking, referrer, and permissions hardening headers.
- Production source maps are not generated by the Vite build; Vercel Protected Sourcemaps remains enabled.
- Secrets remain server-side. `.env*` and `.vercel` are ignored by Git, and no `VITE_*` secret is used.

## Intentional availability states

During development, production may be paused to prevent public access. Before submission or judging it must be resumed and tested anonymously because the official rules require an incognito-accessible live demo.

Vercel Authentication currently protects generated `vercel.app` deployment and preview URLs while custom production domains are excluded. This is useful during development, but the canonical custom domain remains the required judge-facing entry point once the project is resumed.

## Pre-submission checklist

1. Confirm `Hackathon-FG` has accepted read access to the private GitHub repository.
2. Resume the Vercel project.
3. Open the canonical custom domain in a logged-out incognito window.
4. Confirm the home page, lazy chunks, and `/api/health` load without Vercel membership.
5. Confirm both judge-facing domains resolve to the same current deployment.
6. Confirm a live scan succeeds once, then avoid repeated paid verification.
7. Verify replay, Portfolio Ops, MCP, and the guided tour.
8. Confirm no secrets appear in browser JavaScript, responses, logs, or documentation.
9. Leave the deployment active through the stated judging period.

## Incident indicators

Requests for `/wp-admin/install.php`, `/wp-login.php`, `/xmlrpc.php`, or `/products.json` are common automated internet probes and do not by themselves establish compromise. Investigate when they coincide with unexpected vendor-credit use, Supabase mutations, sustained function traffic, authentication failures, or secret disclosure.

## Emergency response

If paid-endpoint abuse is observed:

1. Pause the project or enable Vercel Attack Mode.
2. Inspect FortyGuard usage, Vercel function paths, and Supabase writes.
3. Rotate only credentials that may have been exposed.
4. Preserve logs and timestamps.
5. Tighten or disable the affected endpoint before resuming.
