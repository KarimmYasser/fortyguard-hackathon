# Database Query Performance and Replay Persistence

> **Scope:** Application-side findings from the Supabase Query Performance report and the remediation shipped in commit [`171ff5e`](https://github.com/KarimmYasser/fortyguard-hackathon/commit/171ff5e).  
> **Production data store:** Supabase PostgreSQL through PostgREST.  
> **Local fallback:** SQLite; it is not durable on Vercel.

## 1. Executive summary

The performance report mixed two different classes of SQL:

1. **Supabase platform and dashboard introspection**, such as reads from
   `pg_available_extensions`, `pg_timezone_names`, `pg_proc`, and catalog/table
   metadata. These queries are generated by Supabase tooling. They are not issued
   by Thermal Sentinel Grid and cannot be optimized in this repository.
2. **Application PostgREST traffic**, including cache reads, table counts, and
   writes to `substation_telemetry_logs` and `cbf_safety_certificates`. These were
   actionable.

The largest avoidable application behavior was write amplification on the
canonical replay endpoint. Loading the dashboard called the deterministic replay
GET, which recomputed a fixed checked-in fixture and then appended the same 12
modelled telemetry steps plus a newly generated safety certificate. A read-only
page refresh therefore mutated the production audit database.

The fix makes the replay GET read-only and narrows PostgREST projections used by
cache retrieval and database-health counts. It does **not** claim to optimize the
Supabase-owned catalog queries.

## 2. Root cause

`GET /api/v1/replay/phoenix-2023` serves a deterministic calculation based on the
checked-in Phoenix fixture. Before the fix, each request also:

- inserted 12 rows into `substation_telemetry_logs`; and
- persisted a generated row in `cbf_safety_certificates`.

These writes did not represent a new scan, operator action, or unique simulation.
They represented another view of the same replay. Traffic, refreshes, guided-tour
navigation, and serverless cold starts could therefore grow both tables without
adding evidence.

The same report exposed two unnecessarily broad read patterns:

- Supabase cache lookup selected every `api_call_cache` column even though the
  caller only needed `response_payload`;
- the Cloud DB status endpoint counted rows with `select=*`, including tables
  containing large JSON payloads, although only an exact count was needed.

## 3. Implemented changes

### 3.1 Deterministic replay is read-only

[`src/server/routes/replay.py`](../../src/server/routes/replay.py) no longer calls
telemetry or certificate persistence methods. The route still generates the full
baseline-versus-mitigated response and retains its edge-cache policy:

```http
Cache-Control: public, max-age=0, s-maxage=600, stale-while-revalidate=86400
```

Replay evaluation internally buffers a safety certificate because the shared
safety-gate component also supports mutation-oriented workflows. The GET route
clears that in-memory buffer after response generation instead of writing it or
leaving it queued on the process-wide replay engine.

This is an HTTP-semantics correction as well as a performance optimization: a
safe, idempotent GET no longer creates database records.

### 3.2 Cache lookup uses a narrow projection

The Supabase branch of `get_cached_api_call()` now requests:

```text
select=response_payload
```

instead of `select=*`. The SQLite branch was already narrow enough to decode the
stored payload. Cache behavior is unchanged: a hit returns the complete cached
response, while a miss falls through to the caller's live or deterministic work.

### 3.3 Database counts project indexed identifiers

`HybridDatabaseManager._supabase_select()` now accepts an explicit `columns`
projection, defaulting to `*` for existing callers. `_supabase_count()` requires a
count column and sends a `HEAD` request with:

```text
Prefer: count=exact
Range: 0-0
select=<primary-key>&limit=1
```

PostgREST reports the exact total in `Content-Range`; the response body is not
materialized. `get_database_status()` maps each of the 17 application tables to
its primary key, including:

| Table | Count projection |
| :--- | :--- |
| `api_call_cache` | `query_hash` |
| `substation_telemetry_logs` | `id` |
| `cbf_safety_certificates` | `certificate_id` |
| `microclimate_parcel_store` | `parcel_id` |
| `simulation_runs` | `simulation_id` |

The implementation contains the complete 17-table mapping, including `validation_runs` projected by `validation_id`. Supabase counts remain
authoritative when configured; SQLite counts are still reported as local fallback
state.

## 4. Persistence policy after the fix

The change does **not** disable persistence globally. It separates viewing a
frozen replay from creating new operational evidence.

| Workflow | Persistence behavior |
| :--- | :--- |
| View canonical Phoenix replay | Read-only; no telemetry or certificate inserts |
| Repeat identical deterministic sandbox solve | Return permanent `api_call_cache` result keyed by full request identity |
| Run a new What-If solve | Persist the complete result and compact simulation audit according to the simulation route contract |
| Complete a live FortyGuard scan | Persist measured parcel/provenance data and reusable API responses |
| Execute mutation-oriented safety/dispatch workflow | Persist the workflow's trace, work order, or certificate at its owning write boundary |
| Accept a live external-validation report | Insert the content-addressed report into `validation_runs`; duplicate identities are ignored |
| Open Cloud DB status | Read exact counts using primary-key projections |

Historical duplicate rows are not deleted by this change. Production deletion
requires a backup, an exact identification predicate and count, and explicit
approval.

## 5. Regression guards

The test suite now verifies the relevant contracts:

- cache lookup requests only `response_payload` from Supabase;
- database status supplies a narrow primary-key projection for all 17 tables;
- the replay route AST contains no database or safety-certificate persistence
  call; and
- replay execution emits no swallowed persistence warnings.

Validation at implementation time:

```text
Backend test suite:       168 passed, 3 opt-in live tests skipped
Frontend production build: passed
Git whitespace check:      passed
```

Tests clear Supabase credentials in [`tests/conftest.py`](../../tests/conftest.py),
so validation does not write to production or consume FortyGuard credits.

## 6. How to interpret future Supabase reports

Do not rank a pasted report solely by total execution time. First identify the
query owner.

### Platform/dashboard queries

Typical signatures include PostgreSQL catalog relations and Supabase metadata:

- `pg_available_extensions`
- `pg_timezone_names`
- `pg_proc`, `pg_namespace`, `pg_class`, or `information_schema`
- pgMeta-generated schema introspection

These often become prominent while the Supabase dashboard is open. Close the
relevant dashboard view and compare a production-only time window before treating
them as application regressions.

### Application queries

Application traffic generally appears as PostgREST-generated SQL against one of
the 17 documented tables. Investigate:

- repeated inserts with identical business meaning;
- `select *` against JSON-heavy tables;
- unbounded reads or missing filters;
- high call count even when mean latency is small;
- GET requests that mutate state; and
- counts that retrieve rows instead of using headers/projections.

The report supplied during this audit was duplicated in the pasted input. Its
percentages and call counts must therefore be evaluated as one report, not summed
across both copies.

## 7. Production verification checklist

After deployment, verify behavior without deleting records:

1. Record current counts for `substation_telemetry_logs` and
   `cbf_safety_certificates`.
2. Request `GET /api/v1/replay/phoenix-2023` several times.
3. Confirm the response remains HTTP 200 and contains the expected 12-step replay.
4. Re-read both table counts and confirm they are unchanged.
5. Open **Cloud DB (17 Tables)** and confirm all counts load.
6. Inspect network requests or PostgREST logs and confirm cache hits project
   `response_payload`, while count requests project each table's identifier.
7. Compare a fresh Supabase performance window after normal application traffic;
   exclude dashboard/catalog introspection from application conclusions.

This checklist validates the query shape and absence of replay writes. A claim of
measured latency or database-time improvement should only be made after collecting
a comparable post-deployment window.
